## wfl_parser_textx.py
```bash
python3 wfl_parser_textx.py grammar.tx base.wfl
# Output: output_textx.txt
```
**Dependencies:**
- textX

This Parser uses a defined grammar.tx (defines grammar used by feature models of Waflle) to parse .wfl files like base.wfl. The Class provides a parse_feature() method for parsing the features of the feature model and then return a List of feature dimensions used for pairwise sampling. parse_min_max() and parse_enums() both return a dictionary mapping min max values to specific features (also parsed from the feature model) and a dictionary mapping attribute names to a list of valid values.

## pairwise_generator.py
```bash
python3 pairwise_generator.py grammar.tx base.wfl
```
**Dependencies:**
- allpairspy

This script uses 2-wise sampling to generate configurations from the list of feature dimensions (output of of wfl_parser_textx.py). By this we get a set of configurations that contain every pair of feature choices at least once. Extracted feature dimensions are extended by an extra dimension of the 9 context variants (2-float-so, ...) which define the type of search space and number of objectives for the experiment. Each configuration is stored in a PairwiseConfig dataclass.

## selenium_validator.py

**Dependencies**
- selenium
- webdriver-manager

This script is an automated browser script that turns the output of **pairwise_generator.py** into real BRISE configurations by navigating through the Waffle UI. For each **PairwiseConfig** it opens a new chrome browser window and visit the Waffle UI (localhost:8000). It loads the appropriate feature model (2-float-so.wfl, ...) into the UI und then processes through the staged configuration step by step. At each step there are either from fields presented which are automatically filled with the dedicated values. Because **pairwise_generator.py** is not constraint aware, some generated configurations will be naturally invalid. These will be detected the Waffle. But because of this, the amount of invalid configs can be so high, that the output is too small and not suited for integration testing. To avoid too much invalidations, WFL_CONFLICTS have been defined to handle specific configurations.

For exmaple: A PairwiseConfig can contain multiple Algorithms for the Optimizer each having a own constraint and creating conflicts. There are some cases where no legal value for e.g. **PopulationSize** that satisfy the various Algorithm constraints. That's why the selenium validator handles this by not selecting specific features when other conflicting features have already been selected.

After completing all steps a configuration is either downloaded as a valid configurations and put into the **output_configs/** directory or the configuration is rejected because of a constraint validation error, which is then looged in **invalid_configs.log**. The browser is then closed and the next configurations goes throught the same process. At the end the **output_configs/** directory contains the .json files that passed Waffle's staged configurations, which can then be used as Experiments for BRISE.

Start a running instance of BRISE first, which also runs an instance of the Waffle UI to generate real BRISE configurations:
```bash
./brise.sh up -m docker-compose
```

Run all 85 configs:
```bash
python3 selenium_validator.py
```

Run first N configs:
```bash
python3 selenium_validator.py 25
```

Run a range (configs 25–49):
```bash
python3 selenium_validator.py 50 25
```

Run a single config (e.g. config 17):
```bash
python3 selenium_validator.py 18 17
```

## quant_metrics.py
This script provides quantitative metrics for this Phase to measure how well BRISE's feature model is covered. These quantitative metrics serve the purpose of assessing the effectivness of this approach.

The metrics are:

### Group 1 Basic feature metrics:
- **feature dimensions: 49** -> the number of decision points extracted from the feature model
- **total feature values including .None features: 110** -> the number of selectable features across all feature dimensions (.None features represents a feature not being selected in an optional or xor feature group)
- total feature values excluding .None features: 76

### Group 2 Pairwise Generation:
- **Test Suite Size (TSS)/Configurations: 85** -> number of configurations generated by pairwise sampling
- **Feature coverage of pairwise sampling (including and exlcuding .None): 100%** (as expected)

### Group 3 Configuration Space Reduction (CSR):
Calculates the reduction from the number all possible combinations to the number configurations generated by pairwise sampling.
- **exhaustive (number of possible combinations): about 1.28 x 10^17**
- **CSR ratio: 6.63 x 10^-16** -> means that the reduction to 85 generated configs in pairwise_generator.py is nearly 100%
Telling us that pairwise sampling is strongly efficient sampling strategy for BRISE's feature model

### Group 4 Feature coverage and Invalid Configuration Ratio (ICR):
- **Valid configurations: 24 of 85 total** -> number of configs which are valid and contain no constraint validation (produced by Waffle)
- **ICR: 71.8%** -> the majority of produced configurations from pairwise sampling produces invalid configurations
- **feature coverage including .None: 58.2%** -> meaning that the entirety of valid configurations contain 58.2% of all possible features
- **feature coverage excluding .None: 84.2%** -> meaning that the entirety of valid configurations contain 84.2% of all possible features exluding .None (exluding the absence of features)
- **uncovered features: 12** -> a list of features that do not appear in any valid configurations excluding .None

### Group 5 Jaccard distance
Jaccard distance tells us how similar all 24 valid configurations are. A distance of 0 would mean that two configts contain exactly the same set of features while a distance of 1 means that two sets of features share no similarity. Too much similarity would mean that the test suite is pretty redundant.

- **average distance: 0.28** means that the average pair of configs differ in about 28% of their features (JSON keys), which is bound to the general structure of BRISE experiments/configurations as all valid configs share a common pattern of mandatory features
- **min distance: 0.00** means at least one pair of configs is structurally indistinguishable
- **max distance: 0.63** means the most differing pair share only about 37% of their JSON keys

### Group 6 Tuple Occurence
This metrics check wether the 24 valid configs together cover all feasible feature pairs.
- **total pairs: 2776**
- **covered pairs: 58.4%** meaning that about 42% of feature pairs do not appear, likely because of constraints (only 24 out of 85 valid configs)

This means pairwise interactions between features of about 42% are not covered by this test environment which is likely due to the high density of constraints in the feature model.

### Group 7 Redundant configurations (RC)
If a feature pair has already appeared in one valid configuration, any further configurations containing the same pair is redundant from pairwise coverage.

- **excess redundant ocurrences (RC): 7855**
- **redundancy ratio (RR): 2.83** -> on average, each appears about 2.83 more often as necessary
- **effeciency score: 0.17** -> only 17% of tuple-testing effort was productive. The other 83% are retested pairs that had already been seen, which is probably a consequence of of structural similarity

A score of 1.0 would mean, that every pair is only covered by one configurations and appears in no other configuration again.
